# Sink release 后的可靠性检查（2026-09-09）

检查范围：Sink `v0.10.2`（`d5bf7b7`，2026-09-08 发布）至
`878b24894b6476c8b30771e83bbd73f6ccfcdaaf`，配套 sink-go `7ca6ae8`，
production-suite `c4d7554`。本次工作以这些版本加本地修改进行验证。

## 发现并修复的问题

| 问题 | 真实业务影响 | 修复与回归证据 |
| --- | --- | --- |
| MongoDB Query 把判断 `has_more` 的额外文档计入结果预算 | 当前页只有小记录，但下一页第一条很大，当前页也会失败，无法正常分页 | 只对实际返回的文档计费；find 和 aggregate 都复现旧错误。下一页真正返回大文档时仍必须完整失败。取消和预算失败后，真实 MongoDB cursor 必须关闭。 |
| 搜索响应缺失完成信息会被当成成功 | 网关或异常响应缺少 `timed_out`、`_shards` 等字段时，Query/Count/Scan 可能暴露不完整数据，甚至把异常响应当成遍历结束 | 必须明确未超时、全部分片成功；字段缺失、null、计数不一致均失败。代理修改真实 ES/OpenSearch 响应，检查无输出、无重试、后续正常请求可恢复。 |
| 跨集群搜索忽略被跳过的远端集群 | 即使 HTTP 200 且所有已报告分片成功，数据仍可能少一个集群 | 检查 `_clusters` 完成状态，拒绝 skipped/partial/running/failed；测试完整集群响应仍被接受，并将跳过集群的响应加入公开 API 故障矩阵。 |
| MongoDB Query 允许 `allowPartialResults: true` | 分片不可用时，调用方可能得到缺少记录的“正常”页面 | 在发送命令前拒绝此选项；保留 false。增加命令验证和公开 Dataset API 回归。没有用单节点测试冒充分片宕机验证。 |
| 定时 fuzz 可在未进入变异阶段时返回 PASS | 历史覆盖语料较多时，测试时间全部耗在加载语料，流水线仍显示成功 | 增加 fuzz 进度门禁及日志，CI/release 默认每个 fuzzer 三分钟。用 1ns 预算验证：Go 返回 PASS，但套件必须失败。 |

旧版本敏感性证明：用 `878b248` 的独立二进制运行公开 API 用例
`TestNativeRejectsIncompleteBackendResults/elasticsearch/Query/missing-timeout`，
实际触发“failed Query exposed an apparently valid page”断言。
证据检查器确认失败来自指定断言，而不是构建失败、跳过或基础设施缺失。
此案例已加入未来的历史版本敏感性门禁。

跨集群跳过远端但仍返回结果的行为依据
[Elasticsearch 官方文档](https://www.elastic.co/docs/explore-analyze/cross-cluster-search)。
本次通过响应故障注入验证 Sink 的处理逻辑，没有搭建真正的跨集群网络分区。

## 新增的业务场景

- 七个存储配置都运行正序、倒序 Scan：删除下一条尚未读取的记录，更新另一条未读记录，在检查点两侧插入记录；按独立的期望序列检查结果。
- 在两个 Sink 实例之间交替请求，将页大小从 2 改为 1 或 3，再重放原检查点；检查不丢失、不重复、能看到后续更新。
- 已取消请求和损坏的 cursor 必须失败，同时不能破坏仍有效的原检查点。
- MongoDB 有序、无序批量插入遇到重复键；失败响应保留原始数据库字段，成功部分符合各自的执行语义。
- 单成员 MongoDB 副本集请求 `w:2`，实际触发写关注超时；返回失败，同时确认已经写入的数据仍在。
- MongoDB Query 在收到初始 cursor 后取消、或因结果预算失败，必须丢弃整页输出并发送 cursor 清理。

重复键和写关注超时的新增测试确认现有 Execute 实现已经正确；这两项没有修改生产逻辑。

## 验证记录

- Sink、sink-go、production-suite 默认全量 race 测试通过。
- Sink 和 suite 的 vet/staticcheck、格式和 diff 检查通过；配套 protobuf 合同一致。
- 完整 MongoDB ReplicaSet integration 通过，包括新增的预算、部分写入、写关注超时和 cursor 清理案例。
- 七存储业务矩阵、独立操作模型、双 Kafka 路由、代表性负载、worker 重启、三分钟活动故障、积压清空和死信修复重放通过。生产套件记录 94 个成功测试事件（包含子测试及分阶段重复执行），无失败或跳过。
- 完整公开 API conformance 通过：249 个成功测试事件，789 秒，无失败或跳过。最后追加跨集群检查后，重新运行全部原生 API 定向回归：73 个成功事件、65 秒，无失败或跳过；并重跑最终服务端全量 race 和 lint。
- Fuzz：Kafka envelope 15 秒执行 208,308 次；产品模型 180 秒执行 2,263 次并发现 17 个新覆盖输入；offer 模型也已进入实际变异阶段并通过。各 fuzzer 的计数包括语料执行，不能解释为等量的独立业务场景。1ns 预算的负例被新增门禁正确拒绝。
- 新增历史回归敏感性案例和 fuzz 假通过负例均已验证；本次没有重跑其余六个历史版本证明。

测试 runner 保留 Compose 配置、候选程序日志、故障时间、指标和 JSON 测试事件，
并打印证据目录。CI 按 workflow 的 artifact 规则保存证据；本次本地运行创建的
临时容器和卷已清理。

## 覆盖边界

当前测试覆盖业务语义、并发历史、局部故障、资源归属和进程崩溃，不能视作所有生产条件的穷尽证明。

- 本次运行的是短时发布资格测试，没有执行两小时持续测试。
- MongoDB 分片故障、真实多节点副本集选主、跨机房网络分区、磁盘满和备份恢复仍需部署环境专项验证。
- Scan 是实时 seek 遍历：检查点之后的数据变化会影响结果，不能用于要求一致快照的导出。搜索排序字段必须稳定，并带唯一的排序字段；重建数据集后的恢复语义不在本次验证范围内。
- 业务侧处理页面、产生外部副作用、保存检查点之间的崩溃窗口，以及业务幂等性，需要在具体应用中测试。Sink 的 Kafka 交付仍是至少一次。

服务端修复与增强套件需配套交付。Sink 的 CI、release 和 reliability workflow
应固定到包含本次测试的同一个 suite 提交，以保持测试代码和工作流一致。
